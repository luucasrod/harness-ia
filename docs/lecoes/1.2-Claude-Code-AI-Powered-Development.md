## INTRODUÇÃO

Claude Code é um CLI que executa Claude (LLM) diretamente em seu terminal com acesso a ferramentas especializadas: leitura/edição de arquivos, execução de Bash, busca em codebase, etc.

**Conceito crítico:** Claude Code não é "IA escrevendo seu código". É você usando uma IA como assistente arquitetônico e de produtividade - semelhante a pair programming remoto, mas o pair program é um modelo de linguagem.

### Diferença Entre Abordagens

| Abordagem | O que funciona | O que falha |
|-----------|---|---|
| **"IA escreve tudo"** | Boilerplate, scaffolding, refactoring automático | Lógica de negócio complexa, decisões de arquitetura |
| **Claude Code profissional** | Arquitetura, design patterns, code review, testes | Raciocínio crítico sobre requisitos |
| **Seu trabalho manual** | Requisitos, trade-offs, segurança, decisões | Boilerplate, transformações repetitivas |

## SEÇÃO 1: CLAUDE CODE COMO FERRAMENTA (15 MIN)

### 1.1 Os Três Workflows Principais

#### **Workflow 1: Pair Programming com Claude**

**Cenário:** Você tem um requisito complexo e quer explorar design options antes de escrever código.

```bash
claude-code
# Terminal interativo abre

You: "Tenho uma tabela `users` com 10M de registros. Preciso adicionar 
uma coluna NOT NULL sem downtime. Quais trade-offs existem?"
```

Claude analisa sua estrutura existente (se você compartilhar), sugere:
- Blue-green deployment
- Backfill com default value
- Particionamento
- Read replicas durante migração

**Seu trabalho:** Avaliar trade-offs, escolher estratégia, implementar.  
**Trabalho de Claude:** Exploração arquitetônica + code generation após decisão.

#### **Workflow 2: Code Review Estruturado**

**Cenário:** Você escreveu código, quer feedback antes de merge.

```bash
claude-code
# Compartilhar o arquivo ou diff
```

Claude foca em:
- **Bugs lógicos:** off-by-one, race conditions, null handling
- **Security:** SQL injection, auth bypass, data exposure
- **Performance:** N+1 queries, memory leaks
- **Style:** Consistência com projeto, reuse, testability

**Não confia em:** Tudo que envolve requisitos de negócio ou decisões estratégicas.

#### **Workflow 3: Refactoring + Scaffolding**

**Cenário:** Código funciona mas está bagunçado. Quer limpar.

```bash
claude-code
# Compartilhar estrutura caótica
# Claude propõe: arquitetura, extração de funções, module boundaries
# Você aprova as mudanças, Claude executa refactoring (com Edit/Write)
```

**Força:** Claude é muito melhor em reconhecer padrões repetitivos e sugerir abstrações.

Claude é excelente em:

- Gerar boilerplate e scaffolding

### 1.3 Trade-offs Críticos: Quando NÃO Usar Claude

#### ❌ **NÃO use para lógica crítica de segurança**

```typescript
// ❌ NUNCA deixe Claude escrever sozinho:
export function hashPassword(password: string): string {
  // Claude pode gerar código que "parece" certo mas tem timing attacks
  // ou usa algoritmo errado. Use bibliotecas estabelecidas.
}

// ✅ CERTO:
import bcrypt from 'bcrypt';

export async function hashPassword(password: string): Promise<string> {
  return bcrypt.hash(password, 10); // Você define salt rounds
}
```

**Por quê?** Segurança tem "armadilhas desconhecidas" que Claude não pode saber. Use bibliotecas testadas.

#### ❌ **NÃO use para arquitetura sem validação**

Claude vai gerar "alternativa A vs B vs C" rapidamente, mas a decision decision é sua:

```bash
# ERRADO:
Claude: "Recomendo migrar para microserviços"
Você: "Ok, faz aí"

# CERTO:
Claude: "Aqui estão 3 arquiteturas: monolito escalado, 
        microserviços com message queue, ou serverless. 
        Trade-offs de cada: [...]"
Você: "Faz sentido? Custa quanto? Risco? Passos de migração?"
Claude: "[análise profunda]"
Você: "Vamos com a opção 2 porque [motivo de negócio]"
```

#### ❌ **NÃO ignore testes só porque Claude gera código**

```python
# Claude gera:
def calculate_invoice_total(items):
    return sum(item.price * item.quantity for item in items)

# Parece correto. Mas testes você escreve:
def test_invoice_discount_applied():
    # Seu teste revela: código ignora cupom de desconto!
    # Claude não sabia do requisito
```

### 1.4 Métrica: Quando Claude Agrega Valor

**Alto valor:**
- Você tem requisito claro → Claude explora implementações
- Seu código existe → Claude revisa ou refatora
- Padrão é comum → Claude scaffolding é rápido

**Baixo valor:**
- Requisito vago ou incompleto → Você precisa clarificar primeiro
- Lógica muito novel → Você design, depois Claude implementa
- Contexto de negócio é crítico → Seu trabalho antes

### 2.1 A Anatomia de um Bom Prompt

Um bom prompt para Claude tem:

1. **CONTEXTO:** Arquivo, branch, padrões do projeto
2. **PROBLEMA:** O que precisa resolver (específico, não vago)
3. **RESTRIÇÕES:** O que é não-negociável
4. **FORMATO:** Como você quer a resposta

```markdown
# ESTRUTURA RECOMENDADA

## Contexto
[arquivo de código, requisito, decisão anterior]

## Problema
[Descrição específica do que precisa fazer]

## Restrições
- TypeScript (sem `any`)
- Deve ser backward-compatible
- Sem dependências externas novas

## Formato esperado
[Mude este arquivo: /src/auth.ts]
[Crie novo arquivo: /src/utils/tokenizer.ts]
```

#### **🌟 EXCELENTE**

```markdown
## Contexto
Projeto Next.js 14, PostgreSQL + Prisma v5.x.
NextAuth v5 configurado em /app/api/auth/[...nextauth]/route.ts

Considere isso - não volte pra JWT.

## Problema
User Story: "Como usuário, quero fazer login com email/senha e manter sessão"
Critério de aceitação:
- [ ] Email inválido → erro 400
- [ ] Senha errada → erro 401 (não revela se email existe)
- [ ] Login bem-sucedido → sessão criada, redirect /dashboard
- [ ] Session persiste em aba nova (não só memória)
- [ ] Logout limpa session

## Restrições
CRÍTICAS:
- Não usar bcrypt.compare diretamente (timing attacks). Use comparePasswords() em /lib/auth.ts
- Session httpOnly + SameSite
- Rate limit: max 5 login attempts por 15min por IP

NICE-TO-HAVE:
- Rememberme checkbox (extend session 30 dias)

## Testes Esperados
Deve passar:
- auth.test.ts (já existe)
- e2e/login.spec.ts (já existe)

## Resultado esperado
POST /api/auth/callback/credentials recebe { email, password }
Retorna 200 + session cookie, ou 401/400 + msg de erro

Se tiver conflito com código existente, mencione que não entendeu.
```

**Resultado:** Claude tem contexto de verdade, segue padrões do projeto, evita armadilhas.

## SEÇÃO 3: CODE REVIEW COM IA (10 MIN)

### 3.1 Como Estruturar um Code Review

```bash
claude-code
# Compartilhe:
# 1. Arquivo completo (melhor) ou diff
# 2. Contexto: "Isso resolve PR #123"
# 3. Foco: "Revisar segurança de queries" ou "gerais"
```

### 3.2 Exemplo Real: SQL Injection Risk

**Seu código (suspeito):**

```javascript
// ❌ VULNERÁVEL
function getUserByEmail(email) {
  return db.query(`SELECT * FROM users WHERE email = '${email}'`);
}

// Você submete pra Claude revisar
```

**Claude identifica:**

```
CRÍTICO: SQL Injection
Email = "'; DROP TABLE users; --"
Resultado: Tabela deletada.

CORREÇÃO:
Use prepared statements (Prisma, já instalado):
db.user.findUnique({ where: { email } })

Ou parameterized queries:
db.query('SELECT * FROM users WHERE email = $1', [email])
```

### 3.3 Exemplo: Race Condition

```typescript
// ❌ RACE CONDITION
export async function claimCode(userId: string, code: string) {
  const claim = await db.code.findUnique({ where: { code } });
  
  if (claim.used) throw Error("Já usado");
  
  // ⚠️ Entre aqui e a linha de baixo, outro request pode usar o code!
  
  await db.code.update({ data: { used: true, userId } });
}

// Claude detecta:
// "Dois requests simultâneos podem passar no if(). 
//  Use transaction + row-level lock:
//  db.$transaction(async tx => {...})"
```

### 3.4 O Que Claude Review FAZ BEM

✅ **Bugs detectáveis por padrão:**
- Off-by-one em loops
- Null pointer dereferences
- Resource leaks (files não fechando)
- SQL injection
- Race conditions
- XSS vulnerabilities

✅ **Code Quality:**
- Nomes de variáveis ruins
- Funções muito longas (>50 linhas, reuse)
- Commented code (remover)
- Imports não usados

✅ **Performance:**
- N+1 queries
- Loops desnecessários
- Memory leaks óbvios
- Cache invalidation

### 3.5 O Que Claude Review FAZ MAL

❌ **Não confie em:**
- Lógica de negócio complexa (Claude pode não entender regra)
- Requisitos implícitos (se código "parece errado" mas atende spec)
- Testabilidade (precisa você testar)
- Escalabilidade em cenário específico (depende de números)

**Regra:** Se você suspeita que Claude entendeu errado, **sempre** valide.

## SEÇÃO 4: ARQUITETURA COM SUPORTE DE IA (10 MIN)

### 4.1 Design Decisions: Como Claude Ajuda

**Cenário:** Você precisa armazenar 100M eventos/dia. Como?

**Seu trabalho:** "Qual é o padrão de query?"  
**Claude:** Explora opções...

```markdown
## Opção A: PostgreSQL com retention policy
PROs: ACID, simples, sem infra nova
CONTRAs: storage cresce 36B/ano, backup pesado

## Opção B: TimescaleDB (extension Postgres)
PROs: Otimizado para séries temporais, retention automático
CONTRAs: Vendor lock-in relativo, outro software

## Opção C: ClickHouse
PROs: Compressão 10x, queries analíticas rápidas
CONTRAs: Não-ACID, eventual consistency, infra nova

## Opção D: S3 + Athena
PROs: Ilimitado, pay-per-query, serverless
CONTRAs: Latência alta (30s+), queries complexas lentas
```

**Seu trabalho:** Entender trade-offs, escolher.

### 4.2 Geração de Alternativas

Claude é excelente em brainstorm arquitetônico:

```bash
Claude: "Para cache distribuído, considere:
        1. Redis (low latency, low volume)
        2. Memcached (simples, mais volumoso)
        3. DynamoDB (serverless, cara)
        4. Application-level cache + invalidation strategy
        
        Qual padrão de acesso você tem?"

Você: "80% reads, 2% writes, 1M chaves"

Claude: "Priorize Redis. Invalidation strategy:
        - TTL 1h para reads
        - Active invalidation no write (pub/sub)

```

### 4.3 Trade-off Analysis

```markdown
# Decision: Monolito vs Microserviços

## Monolito (status quo)
| Aspecto | PRO | CONTRA |
|---------|-----|--------|
| Deployment | 1 artefato, simples | Downtime em deploy |
| Scaling | Vertical (mais máquina) | Acoplamento limita escala |
| Dev | Sem network latency | Testes integrados mais lentos |
| Debug | Stack trace completa | Código montuoso |
| Custo | Baixo (1 processo) | Aumento exponencial |

## Microserviços
| Aspecto | PRO | CONTRA |
|---------|-----|--------|
| Deployment | Independente, zero-downtime | Coordinação N serviços |
| Scaling | Granular (serviço X replicas) | Overhead de orquestração |
| Dev | Simples, isolado | Network latency, eventual consistency |
| Debug | Simples (apenas seu serviço) | Traces distribuído é complexo |
| Custo | Paga só o que usa | Infrastructure + management |

## Recomendação
Monolito até 2-3K rpm de carga.
Microserviços quando: scaling granular crítico OU times independentes.
```

**Seu trabalho:** Validar se análise faz sentido pra seu contexto.

## SEÇÃO 6: CASE STUDIES REAIS

### Case 1: Migração de Database (Migration de Schema)

**Situação:** PostgreSQL, 50M linhas, adicionar coluna NOT NULL.

**Seu trabalho:**
- Entender requisistos de downtime
- Decidir: Blue-green? Zero-downtime migration?

**Claude Code auxilia:**
- Gera SQL de backfill + validation
- Propõe strategy (default value, then NOT NULL, then constraint)
- Revisa plano de rollback

**Código gerado:**

```sql
-- Step 1: Add column com default (permite reads)
ALTER TABLE users ADD COLUMN status VARCHAR DEFAULT 'active';

-- Step 2: Backfill em chunks (não trava DB)
UPDATE users SET status = 'active' 
WHERE user_id > ? AND user_id <= ? + 10000;
-- [Rodado em loop manual, monitorado]

-- Step 3: Remove default, add constraint
ALTER TABLE users ALTER COLUMN status DROP DEFAULT;
ALTER TABLE users ADD CONSTRAINT users_status_not_null CHECK (status IS NOT NULL);

-- Step 4: Validate (0 rows violam constraint)
SELECT COUNT(*) FROM users WHERE status IS NULL;
```

**Resultado:** Schema evolui sem downtime. Você valida em cada passo.

#### **Exemplo de Saída**

**Arquivo gerado:**

```typescript
// /app/api/users/[id]/route.ts
import { auth } from "@/lib/auth"; // seu auth
import db from "@/lib/db";
import { z } from "zod";

const UpdateSchema = z.object({
  name: z.string().min(1).max(100),
  bio: z.string().max(500).optional(),
  avatarUrl: z.string().url().optional()
});

export async function PATCH(
  req: Request,
  { params }: { params: { id: string } }
) {
  try {
    const session = await auth();
    if (!session?.user?.id) return new Response("Unauthorized", { status: 401 });
    
    // Apenas próprio user
    if (session.user.id !== params.id) {
      return new Response("Forbidden", { status: 403 });
    }
    
    const body = await req.json();
    const data = UpdateSchema.parse(body);
    
    const user = await db.user.update({
      where: { id: params.id },
      data
    });
    
    return Response.json(user);
  } catch (e) {
    if (e instanceof z.ZodError) {
      return Response.json({ error: e.errors }, { status: 422 });
    }
    return Response.json({ error: "Server error" }, { status: 500 });
  }
}
```

## TAKEAWAYS PRINCIPAIS

### 1. **Claude Code é Ferramenta, Não Mágica**
Você mantém decisões críticas (arquitetura, segurança, negócio).  
Claude fornece exploração rápida + boilerplate + refactoring.

### 2. **Contexto é Tudo**
Bom prompt = resultado bom.  
Contexto incompleto = ganha aleatório.

### 3. **Iteração é Normal**
Raramente é perfeito na primeira.  
Feedback loop rápido: você valida → Claude refina → repeat.

### 4. **Sua Responsabilidade Permanece**
- Você decide requisitos
- Você valida lógica de negócio
- Você testa criticamente
- Você assume responsabilidade pelo código

### 5. **Conhecer Limitações é Poder**
Claude é ótimo em:
- Boilerplate e scaffolding
- Code review (bugs de padrão)
- Refactoring
- Exploração arquitetônica

Claude é péssimo em:
- Requisitos vagos
- Segurança crítica (sem revisão)
- Lógica de negócio complexa
- Decisões sem contexto
